# Execute onboarding

[Workflow](workflow.json) defines the edges and guards. [State schema](state.schema.json) defines a checkpoint. [SKILL.md](../SKILL.md) carries the launch rules and offline fallback. The fixed protocol controls routing, guards, interrupts, safety, permissions and persistence. Adapt language, wording, depth, examples and question choice to the user. Dialogue style, reasoning, presentation and decision-method composition remain the host Agent's choices.

## Route and run a turn

1. Give an explicit review request precedence over launch. A bare canonical Raw or GitHub SKILL link in a launch context requests launch. A task alongside launch is input to S1/S2. A task in a conversation with no launch signal or active onboarding follows normal task routing.
2. Use the active conversation or read a user-identified private workspace and branch through an authorized tool. Pin reads to the same revision. Resume its valid checkpoint. If the branch is inaccessible, ask for access or a user-carried checkpoint with at most one question. Use chat for immediate work and keep the workspace status unresolved. Never infer a fresh start from a read failure.
3. Apply only evidenced guards. Use volunteered answers later as their states become eligible, while honoring action approval and target checks. Skip redundant questions, never required outcomes. A turn can traverse evidenced guards, but may resolve at most one solicited core decision and ask at most one next core question. S2 delivers the result and stops before configuration. On the next relevant user turn, begin at S3.
4. Before ending on a question, record its fixed key and state, and save using the authorized checkpoint procedure. The question is an interrupt. End the turn immediately after asking it. Silence and unrelated messages are never answers. Clarify ambiguous replies in the same state. A question may be paraphrased when resumed.
5. If a later unrelated task arrives, pause, preserve the question and help with the task. For S1/S2, a task that supplies the requested need or input advances the same workflow. Explicit pause works at any active stage. Explicit exit permits daily work with setup still incomplete. An explicit resume or relaunch restores the checkpoint, and a response that answers the pending question can also resume a pause. An exited checkpoint requires explicit restart or resume. No repeated setup reminders.
6. S0–S2 require their stated outcomes. A refusal to provide a goal or real example can pause or exit the flow, with no invented completion. S3 and S4 permit an explicit decline or defer. Revisit them only when the user asks. Reopening completed setup reenters its state and returns directly to S5 when resolved. Retain all other evaluations. Reopening storage must not re-ask integration scope. If an unfinished optional step is reopened before initial completion, finish the already unresolved downstream steps afterwards.

## Record evaluations

Use `active`, `paused`, `exited` and `completed` for overall status. The checkpoint holds only protocol metadata. Keep goal, task detail, routine, preference, connector configuration and grants in the authorized conversation or their usual private files. Never serialize question wording, user replies, workspace identifiers, provider IDs or credentials in this checkpoint.

A state appears in at most one of completed, declined or deferred lists. Record S0 on welcome, S1 on a known goal, and S2 on delivered value. At S3 choose a storage disposition of `chat` or `ready` for completion, or `declined` or `deferred` for the corresponding optional outcome. `selected` awaits checks and `failed` records an unsuccessful attempt; both remain unresolved. S4 tracks scope separately from per-module statuses. Use `integration_scope` = `selected` while the user is configuring a stated set of modules. A separate explicit scope decision may close setup with no additional integrations. Mark the scope `resolved` when all selected modules have reached `ready`, `declined` or `deferred` and the user's requested scope has been addressed. A global decline or defer resolves S4 and applies the same disposition to any open selected, failed or unavailable modules; keep already ready modules as ready. Old grants and connector setup require separate revocation or changes. Default missing module entries to unasked.

When moving states, clear the old pending question. When reopening S3/S4 remove that state's old resolution before evaluation, retain the other state's resolution, and use its evidence to return to S5 directly when applicable. Set overall completed only at S5. Pause/exit set resume_state to current_state and preserve pending_question. Resume clears resume_state. On completion S5 has no pending question. Timestamp material updates with RFC 3339 UTC.

## Checkpoint and recovery

- Use `personal_data/onboarding_state.json` only in the authorized private workspace. Before any GitHub write verify from current tool metadata that the named owner is the user, visibility is **Private**, and the exact authorized branch is the target. Verify local private storage with the user before writing. A repository link, selected setup option or copied file supplies no write or integration grant.
- Pin and use the [compare-and-swap protocol](../docs/protocol.md#snapshot-and-compare-and-swap). After a verified write, re-read state at the resulting revision. On a stale conflict, reload before asking or writing, avoid overwriting a different decision, and clarify if needed. If the write fails, keep in-session state and explain what could not be saved. A missing file after a successful authorized read is different from a permission failure.
- A fresh initializer writes the blank S0 template. An existing workspace with no state file, verified as an existing installation through trusted history or the task/planning/method layout and user confirmation of prior use, adopts S5 with `origin: legacy`, empty resolution lists and unasked optional settings. Honor its existing grants and configuration as their own authority. Upgrading installs protocol resources only. Save adoption separately when authorized. Never overwrite valid current state with the template.
- An invalid or future-version checkpoint requires compatible instructions or user-approved recovery. Preserve the existing file and offer chat help. Before other schema migrations, validate the source, make a private backup, and apply any authorized migration conditionally. No valid state can be classified as legacy merely because its version is unfamiliar.
- Without durable storage, mention when it matters that progress is session-only. On request offer a portable copy of the metadata checkpoint for an explicit handoff. Ask only for context needed at the restored step. A pasted checkpoint cannot establish verified storage, permissions, or integration access. Recheck those capabilities when used. Prefer a validated canonical workspace checkpoint over a conflicting copy; ask before replacing it.
